# Product_A DB migrations (Aurora PostgreSQL)

Feature: `aws-incident-security-ops-platform` — Task 6.2.

This directory holds the **shared** SQL schema and migrations for the Product_A
Aurora PostgreSQL database (7 tables). It is a top-level `db/` location on
purpose: **both** the Backend API (`apps/backend-api`) and the EKS workers
(`apps/eks-workers`) read/write the same schema, so it must not live under one
consumer's app directory. The `infra/modules/aurora` module deliberately
contains **no schema/migration SQL** (see that module's README), so the schema
is owned here.

## Layout

| File | Purpose |
| --- | --- |
| `0001_init_schema.sql` | Forward (up) migration: creates the 7 tables, indexes, and optional `updated_at` triggers. |
| `0001_init_schema.down.sql` | Optional rollback (down): drops everything created by `0001`. Destroys data — dev reset only. |
| `tests/test_schema_sql.py` | Static (no-DB, no-AWS) checks that the DDL contains the required tables/constraints and no credentials. |
| `tests/test_schema_apply_smoke.py` | Task 6.3 smoke test: applies the migration to a **local** testcontainers PostgreSQL and verifies the 7 tables + key constraints against the live catalog. Skips when Docker/deps are unavailable. |
| `tests/requirements-smoke.txt` | Pinned dependencies (`testcontainers[postgres]`, `psycopg[binary]`) needed only to run the smoke test. |
| `tests/README.md` | How to run the static suite (no Docker) and the smoke test (local Docker). |

Numbering is a zero-padded sequential prefix (`0001_`, `0002_`, ...). Files are
**tool-agnostic plain SQL** so they can later be adopted by a migration runner
without rewriting the DDL.

## The 7 tables and key constraints

| Table | Role | Key constraint | Rationale |

| `incidents` | インシデント本体 | `external_id UNIQUE NOT NULL` | Idempotent ingest against SQS at-least-once redelivery; NOT NULL as the idempotency key must always be present (Req 6.2/6.3, Property 7/8) |
| `incident_comments` | 対応履歴 | `incident_id` FK `ON DELETE CASCADE` | Consistent removal of children when the parent incident is deleted |
| `findings` | セキュリティ Finding | `external_id UNIQUE NOT NULL` | Idempotent finding registration; NOT NULL as the idempotency key must always be present (Req 6.3, Property 8) |

| `alarm_events` | アラームイベント取込 | `external_id UNIQUE NOT NULL` | Idempotent ingest; NOT NULL as the idempotency key must always be present (Req 6.2, Property 7) |

## Migration management strategy (tool candidates)

The migrations are stored as raw SQL to keep them portable. When a runner is
adopted (a later task, out of scope here), any of the following can wrap these
files without changing the DDL:

- **Flyway** — expects `V1__init_schema.sql` naming. The `0001_` prefix maps
  cleanly to a `V1__` rename; the SQL body is unchanged.
- **sqlx (Rust) / golang-migrate** — expect `<version>_<name>.up.sql` /
  `.down.sql` pairs. The current `0001_init_schema.sql` +
  `0001_init_schema.down.sql` already match this up/down convention.
- **Alembic (Python/SQLAlchemy)** — since the Backend API and workers are
  Python (per tasks.md), Alembic is a natural fit. These raw SQL files can be
  invoked from an Alembic revision via `op.execute(...)` / `op.get_bind().exec_driver_sql(open(...).read())`,
  or serve as the reference for autogenerated revisions.

Recommendation for this project: **Alembic**, because the primary schema
consumers are Python (`apps/backend-api`, `apps/eks-workers`). These plain-SQL
files remain the canonical source of the schema; the runner is a thin execution
layer added later.

## Connection and credentials policy (no secrets in this repo)

- These files contain **schema DDL only**. There are no passwords, secret
  values, connection strings, `CREATE ROLE`/`CREATE USER`, or
  `ALTER ... PASSWORD` statements. The static test enforces this.
- The database master credential is **generated and stored by RDS in AWS
  Secrets Manager** (`manage_master_user_password = true` in the aurora
  module). It is never written to SQL, code, tfvars, or this README.
- Applications obtain credentials **at runtime via the secret ARN**, exposed by
  the aurora module output `app_database_secret_arn` (see
  `infra/modules/aurora/outputs.tf`). A future ECS task role / EKS IRSA role
  grants `secretsmanager:GetSecretValue` scoped to that single ARN.
- Aurora lives in the isolated-db subnet and is reachable only from permitted
  application security groups; migrations must run from inside the VPC.

## Execution / operations (conceptual — not run in this task)

Applying migrations requires a live DB connection, which is intentionally **not
performed in Task 6.2**. This task produces files and static verification only.
No `terraform` command, no AWS API call, and no DB connection (psql,
testcontainers, docker) is executed here.

Who applies migrations, and from where (candidates, VPC-internal, credential via
the Secrets Manager ARN above):

- **ECS one-off task** — a short-lived task in a private-app subnet running
  `psql`/Alembic against the isolated-db endpoint. Reuses the same task
  networking and secret access as the Backend API.
- **EKS Job** — a one-shot Kubernetes `Job` in the `workers` namespace using
  IRSA to read the secret, then apply migrations before rolling out workers.
- **CI step (approval-gated)** — a pipeline stage that runs migrations against
  dev after infra apply. Must run inside the VPC (e.g., CodeBuild in the VPC)
  because the DB is isolated.

The schema-apply smoke test (testcontainers PostgreSQL) is **Task 6.3**
(`tests/test_schema_apply_smoke.py`). It applies the migration to a **local**
throwaway PostgreSQL container only — it does **not** connect to AWS/Aurora and
uses no AWS credentials. It skips cleanly when Docker or the smoke deps are
unavailable. See `tests/README.md` for how to run it.

## Applying manually (reference only — do not run as part of Task 6.2)

```sh
# Runs inside the VPC; credentials fetched from Secrets Manager, never hard-coded.
psql "$DATABASE_URL" -f 0001_init_schema.sql

# Rollback (dev reset only — destroys data):
psql "$DATABASE_URL" -f 0001_init_schema.down.sql
```

`$DATABASE_URL` is assembled at runtime from the Secrets Manager secret and the
aurora module's non-secret endpoint/port/database-name outputs. It is never
committed.
